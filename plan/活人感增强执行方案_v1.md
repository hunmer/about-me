# AI 陪伴「活人感」增强系统 · 落地执行方案

**基于**：[AI陪伴活人感增强系统_PRD_v1.1.md](./AI陪伴活人感增强系统_PRD_v1.1.md)
**日期**：2026-10-04
**适配架构**：Memento（Flutter）chat + openai 插件体系
**核心约束**：每个 AI（AIAgent）拥有独立活人感数据；开关挂在每个 AI 自己的配置上（频道默认选中的 AI 即生效对象）

---

## 1. 现状结论（探索结果）

| 事项 | 现状 | 结论 |
|------|------|------|
| AI 聊天链路 | chat 插件只管频道/消息，用户发消息广播 `chat_message_sent`；openai 插件 `ChatEventHandler`（`lib/plugins/openai/handlers/chat_event_handler.dart:52`）订阅后为每个被 @ 的 agent 并行生成回复 | **活人感的唯一拦截点就是 `ChatEventHandler`**，chat 插件几乎零改动 |
| "默认聊天 AI" | 频道级记忆：`channel.metadata.selectedAgents`（`message_input.dart:154-161` 写入，重进频道自动恢复） | 频道默认 AI 天然存在，无需新增全局设置；活人感跟 agent 走 |
| 每 AI 独立数据 | agent 定义共享 `openai/agents.json`；无 per-agent 运行时数据 | 新增 `app_data/openai/aliveness/<agentId>/` 目录实现数据独立 |
| 每 agent 开关机制 | `AIAgent` 已有布尔开关先例（`enableFunctionCalling`、`enableOpeningQuestions`）与 `AgentResourceSlots` 扩展 | 在 `AIAgent` 上加 `alivenessConfig` 字段，风格一致、向后兼容 |
| 消息模型 | 无已读字段、无延迟机制；支持多条消息、`MessageType.audio` 语音类型、`metadata` 自由 Map | 已读用 `metadata` 实现，不改模型；语音/多条直接复用 |
| 定时/后台机制 | reminder 的 `ReminderScheduler`（Timer.periodic 兜底）+ `aboutme_notifications`（系统级调度）；agent_chat 有前台服务；全局 `EventManager` 事件总线 | 主动消息调度直接复用 reminder 模式与通知包 |
| Jev 决策模型 | 真实可用：`POST https://api.typesafe.ai/v1/systemone`，API Key 认证，state + questions（Noul/Choice/Score），返回 choice/probabilities/confidence；无 Dart SDK | 封装 REST 客户端（dio），全局一份配置；**必须带本地规则 fallback** |

## 3. 数据设计

### 3.1 开关与配置：挂在 AIAgent 上（每 AI 独立）

`AIAgent`（`lib/plugins/openai/models/ai_agent.dart`）新增字段：

```dart
final AlivenessConfig? alivenessConfig; // null = 从未配置 = 关闭
```

`AlivenessConfig` 结构（JSON 存于 agents.json 的 agent 条目内）：

```json
{
  "enabled": false,
  "bufferMinSec": 8,         "bufferMaxSec": 45,
  "maxBubbles": 5,           "bubbleDelayMinMs": 800, "bubbleDelayMaxMs": 3000,
  "laziness": 0.5,           // 惰性程度 0-1
  "forgettingHalfLifeDays": 14,
  "proactive": { "enabled": false, "cooldownMin": 60, "dailyLimit": 3, "quietHours": [23, 8] },
  "voice": { "enabled": false }
}
```

> 兼容性：`fromJson` 缺字段时默认 null → 视为关闭；`copyWith`/`toJson` 同步补齐。旧数据零迁移。

**UI 入口**：`lib/plugins/openai/screens/agent_edit_screen.dart` 新增「活人感增强」分组（总开关 + 展开子配置）。chat 中点 AI 头像即可跳到该页（`chat_screen.dart:957-984` 已有跳转），即"当前默认聊天 AI 下有自己的开关"。

### 3.2 每 AI 独立运行数据


## 4. 核心链路改造（ChatEventHandler 接入）

### 4.1 入口分流（最小改动原则）

`chat_event_handler.dart` 的 `_handleChatMessage` 改为：

```dart
final agent = await _agentController.getAgent(agentData['id']);
if (agent?.alivenessConfig?.enabled == true) {
  await AlivenessOrchestrator.instance.handleUserMessage(agent, message, ...);
} else {
  await _processAgentResponse(agentData, message, ...);  // 原路径不动
}
```

> 注意：原代码是先并行起任务再在 `_processAgentResponse` 内 getAgent；改造后提前 getAgent 一次做分流，原函数签名不变。

### 4.2 活人感主流程（Orchestrator）

```
用户消息到达（含 @agent）
 ① BufferService.enqueue(agentId, message)
    - 立即标记已读：originalMessage.metadata['readBy'] += agentId, 'readAt' = ts
      → saveMessage + broadcast('chat_message_updated')
    - 若无占位消息：创建"正在想..."占位（复用现有 typingMessage 模式）
    - 启动/重置缓冲计时器（时长 = f(亲密度, laziness)，夹在 bufferMin~MaxSec）
 ② 缓冲期内新消息 → 并入 buffer，重置计时器（每 agent 每频道一个 timer，可取消）
 ③ 计时器到期 → 组装 state：
    { 缓冲消息数组, agent 状态(energy/intimacy/mood), 时段, 近期记忆摘要 }
 ④ DecisionService.decide(state)：
    - Jev 可用 → 一次调用并行问：是否立即回/延迟秒数/回复策略/是否语音/是否转移话题/用户情绪分
    - Jev 失败或 confidence < 阈值 → 本地规则 fallback（见 5.3）
 ⑤ 按决策分支执行（BehaviorExecutor）：
    - 策略=极简 → 从短回复模板池选（少量情况可调主 LLM 生成一句短回复）
    - 策略=正常/详细/主动转移 → 组装 contextMessages（现有逻辑抽出复用），
      system prompt 追加决策注入段（当前状态 + 指令，如"简短回应，2 句内"）
      → RequestService.streamResponseWithRetry 生成
 ⑥ 生成完成 → 切分多条 → 按延迟逐条 addMessage（第一条替换占位消息，其余新建）
 ⑦ 后台（不阻塞）：写记忆碎片候选、更新 state（能量消耗、亲密度 +δ、互动时间）
```

### 4.3 分条发送实现

- 生成完成后按换行/句末标点（。！？~…）切分，聚合为 1~maxBubbles 条；
- 第一条：直接写入占位消息（现有 token 流式更新即第一条的实时预览）；
- 后续条：`Future.delayed(random(bubbleDelayMin, Max))` 依次 `Message.create` + `addMessage` + `broadcast`；
- 占位消息在流式期间保持"正在输入…"样式（现有 UI 已支持内容实时变化）。

### 4.4 已读机制

- 全部走 `metadata`，不改 `Message` 模型；
- AI 已读：缓冲启动时写 `readBy/readAt`（见 4.2 ①）；
- 用户侧 UI（Phase 3）：消息气泡角落渲染"已读"，订阅 `chat_message_updated` 即可，改动限于 `chat` 的气泡 widget 一处。

## 5. 决策层（Jev + Fallback）

### 5.1 Jev REST 调用（dio 封装，无官方 Dart SDK）

```
POST {jevBaseUrl}
Headers: Authorization: Bearer {jevApiKey}
Body:
{
  "state": {
    "user_messages_buffer": ["最近好累啊", "工作压力好大"],
    "character_energy": 0.45, "intimacy_level": 0.72,
    "current_mood": "low", "time_of_day": "23:10",
    "recent_memory_summary": "用户上周提到加班很多"
  },
  "questions": {
    "should_reply_now":  { "type": "noul",  "question": "缓冲结束后是否应立即生成回复？" },
    "delay_seconds":     { "type": "choice","question": "建议延迟多少秒再发送？", "options": ["0","15","45","120","300"] },
    "reply_strategy":    { "type": "choice","question": "应采用哪种回复策略？", "options": ["极简","正常","详细","主动转移"] },
    "use_voice":         { "type": "noul",  "question": "这条回复是否适合以语音发送？" },
    "should_shift_topic":{ "type": "noul",  "question": "当前是否适合主动转移话题？" },
    "user_emotion_score":{ "type": "score", "question": "用户当前情绪效价", "levels": ["非常负面","负面","中性","正面","非常正面"] }
  }
}
```

响应按类型取 `noul`（0-1）/`choice`+`probabilities`+`confidence`/`score`；`confidence < 阈值(0.65)` 或超时（>1.5s）/异常 → fallback。

### 5.2 决策消费规则（代码硬约束）

- `reply_strategy=极简` 且 `intimacy > 0.4` 才允许模板池直接回复（防冷暴力，PRD 风险表）；
- 延迟取值钳制 ≤ 300s；同一频道 AI 生成任务串行（避免旧流式与分条交叉）；
- 所有决策结果 + 概率追加写 `decisions.log`（可观测性需求）。

### 5.3 本地规则 fallback（离线/无 Key 可用）

```
should_reply_now = energy > 0.3 || intimacy > 0.6
delay = laziness 高 && 消息复杂(>50字) → 15~45s，否则 0
reply_strategy = energy<0.35 → 极简；普通消息 → 正常；用户连发≥3条 → 详细
use_voice = false（fallback 保守）
shift_topic = false（fallback 保守）
```

> fallback 保证：不配 Jev Key 也能开启活人感（纯本地节奏），符合"本地优先"非功能需求。

## 6. 状态机与记忆（摘要）

### 6.1 StateService（Phase 1）

- 每次回复后：`energy -= 0.02~0.05`（按生成长度）、`intimacy += 0.005~0.02`（按用户消息情绪/长度）、更新 `lastInteractionAt`；
- 惰性恢复：读取 state 时按距上次更新时间线性恢复 energy（每天 +0.3，封顶 1.0）；intimacy 随闲置缓慢衰减（半衰期默认 14 天，可配）；
- 阈值影响决策注入：`energy < 0.3` 时 system prompt 注入"你现在很累，倾向简短回应"。

### 6.2 MemoryService（Phase 2）

- 写入：回复完成后后台调主 LLM 一次小请求（限 200 token）提取"值得记的碎片"→ `{content, time, emotionTag, importance, sourceMessageId}`；用户手动标记消息重要（消息长按菜单已有入口可挂）；
- 激活扩散（简化版，无向量库）：碎片带关键词 tags；对话时取最近 2 条消息分词匹配 tags → 一级激活；被激活碎片的关联 tags → 二级加权；取激活分 Top-K（默认 5 条，token 预算 ~300）注入 `recent_memory_summary`；
- 遗忘：`weight = importance * exp(-days / halfLife)`，低于阈值移入归档不删除。

> 不引入向量数据库/图数据库：本地优先 + 最小改动，关键词 + 关联表已满足"聊到才想起"的效果；激活不准的风险靠阈值 + 人工标记兜底（PRD 风险表）。

### 6.3 亲密度问题池（Phase 2）

`lib/plugins/openai/aliveness/data/question_pool.json` 按 PRD 附录 B 分层；Jev/fallback 判断"是否探索+选哪题"，已问过的记录在 per-agent stats，回答后写记忆碎片。

## 7. 主动消息（Phase 3）

- `ProactiveService` + 调度器复用 reminder 模式：`Timer.periodic(1min)` 检查所有 enabled 的 agent：
  - 冷却（stats.cooldownUntil）、每日上限、免打扰时段（quietHours）；
  - 触发条件：`距上次互动 > 阈值 && intimacy > 0.5`，或存在未关闭开环事件（Phase 4），或角色日记产生分享冲动；
- 触发后走同一决策+生成管线，目标频道 = 上次互动频道（metadata 记录）；
- 通知：复用 `aboutme_notifications`（`AboutmeNotifications.instance.scheduleNotification`），点击通知深链打开频道（chat 已支持 channelId 打开：`ChatMainView(channelId:)`）；
- 应用被杀后的严格定时主动消息（生成型）依赖前台服务（复用 agent_chat `ChatForegroundServiceManager` 模式），列为增强项，首版以"应用存活期间"为准。

## 9. 风险与回滚

| 风险 | 应对 |
|------|------|
| 改坏现有聊天 | 分流点唯一且开关默认关闭；enabled=false 代码路径与现在完全一致 |
| 缓冲让用户觉得"卡了" | 占位消息在缓冲期就出现（"正在想…"），且亲密度低时缓冲取下限 8s |
| Jev 不可用/超时 | 1.5s 超时 + 规则 fallback，无 Key 也能用 |
| 分条消息与多 agent 并行写交叉 | 每频道加串行锁（现有 `_processAgentResponse` 并行按 agent 隔离，分条只在本 agent 任务内） |
| 记忆乱联想（Phase 2） | 激活阈值 + Top-K 限制 + 用户手动标记重要 |
| 主动消息骚扰（Phase 3） | 代码级冷却 + 每日上限 + 免打扰时段，三重硬限制 |
